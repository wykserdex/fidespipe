# pefile

Разбор PE-файла (erocarrera/pefile): архитектура образа, таблица секций и
каталог импортов (DLL и символы, включая импорт по номеру).

## Установка донора

Пин объявлен в манифесте (`runtime.requires: ["pefile==2024.8.26"]`) и в
`requirements.lock`, поэтому ставится вместе с плагином:

```
pip install pefile==2024.8.26
```

У pefile нет ни CLI, ни консольного скрипта, поэтому искать бинарь в PATH
бессмысленно: обёртка запускает тот же интерпретатор с фиксированным сниппетом
(`python3 -c`), который импортирует пакет и печатает JSON. Модуль доступен
ровно тогда, когда установлен пакет, то есть проверка «установлен ли донор» не
врёт. Путь к двойнику можно переопределить env `PEFILE_BIN` (имя из PATH или
полный путь) — этим пользуются тесты.

## Порты

| порт | тип | источник |
|---|---|---|
| `file` | string | путь к PE-файлу; на выходе — ровно то, что дал оператор |
| `machine` | string | имя архитектуры **из словаря донора** (`pefile.MACHINE_TYPE`) |
| `machine_id` | number | `FILE_HEADER.Machine` как есть, число |
| `sections` | array | `{name, virtual_address, size, characteristics, flags}` |
| `imports` | array | `{dll, symbols: [{name, ordinal}]}` |
| `section_count` | number | строк в таблице секций |
| `import_dll_count` | number | DLL в каталоге импортов |
| `parser_version` | string | `pefile.__version__` |

Вход: `file` (string, file_ref) и `wall_timeout` (number, optional, 300 с).

Тонкости, из-за которых эти поля выглядят именно так:

- **`machine` пустая строка** означает «эта версия pefile не знает такой код»,
  а не «код потерялся»: `machine_id` при этом заполнен. Раньше обёртка держала
  свою таблицу `MACHINE_NAMES` из 10 кодов, тогда как в `pefile.MACHINE_TYPE`
  их 35 — то есть 25 кодов прежняя обёртка назвала бы `0x0000`. Это вторая
  правда, которая устарела бы первой.
- **`sections[].name`** — имя, обрезанное по NUL. Значения вида `/4`, `/14` —
  не имена: в COFF длинное имя лежит в строковой таблице, а в таблице секций
  стоит ссылка `/<смещение>`. Обёртка отдаёт ссылку как есть и не
  разыменовывает её: разыменование было бы решением обёртки, а не выводом
  донора.
- **`sections[].size`** — `SizeOfRawData`, размер **на диске**, а не
  `VirtualSize` (размер в памяти). В фикстуре у `.bss` они равны 0 и 512.
- **`sections[].flags`** — те же биты `characteristics`, разложенные в имена из
  словаря донора (`pefile.SECTION_CHARACTERISTICS`). Раскладываются только
  однобитовые записи: измерено, что в словаре 31 однобитовая запись и ещё
  11 многобитовых масок выравнивания (`IMAGE_SCN_ALIGN_*`), и по
  многобитовым «маска & запись» дала бы несколько имён сразу. Само число
  `characteristics` отдаётся всегда, поэтому ничего не теряется.
- **`symbols[].name` / `.ordinal`** — имя и/или номер импорта. Импортировать
  можно по номеру, и тогда имени нет: раньше обёртка писала вместо этого
  строку `#17`, то есть выдумывала значение, которого в файле нет.
- **`parser_version`** — без него «импортов нет» неотличимо от «эта версия не
  разобрала каталог импортов». Пустой строкой это не подменяется: репорт без
  версии считается битым.

Наружу не отдаются:

- `FileHeader.TimeDateStamp` — время сборки; не результат, и от него вывод
  меняется между пересборками одного и того же исходника;
- `IMAGE_DIRECTORY_ENTRY_DEBUG` (у pefile это `pe.get_pdb_path()`) — **внутренний
  путь сборки**: абсолютные пути к PDB и каталогам исходников машины, на
  которой файл собрали. Для файла из интернета это ещё и утечка о чужой
  машине. Сниппет этот каталог у pefile вообще не запрашивает, так что отдать
  его нечего даже по ошибке;
- `pe.get_imphash()` — хеш списка импортов: он и есть сигнатура заражения, но и
  идентификатор;
- остальные каталоги PE (ресурсы, TLS, релокации, экспорты) и общие поля
  заголовков (`ImageBase`, `EntryPoint`, `Subsystem`, `DllCharacteristics`) —
  настройки образа, а не то, ради чего плагин запускают.

Поля копируются по списку известных имён: `normalise()` собирает новый словарь
из ожидаемых ключей, а не вырезает запрещённое из репорта донора. Новое поле
донора тогда не может само собой появиться в выводе плагина.

## Сеть

`permissions.network: []` — и это правда, проверено измерением: настоящий
`pefile` запущен на `fixtures/sample.dll` при заблокированных
`socket.connect`, `socket.connect_ex`, `socket.create_connection`,
`socket.getaddrinfo`, `socket.gethostbyname` даёт тот же exit 0 и те же 18
секций / 6 DLL. Контроль блокировки выполняется в том же прогоне (проба
`create_connection` обязана упасть, иначе замер ничего не доказывает). Донор
читает файл — сетевых путей у него нет.

## Тесты

`fidespipe plugin test plugins/community/pefile` — 31 кейс, и они разделены
намеренно:

- **реальный инструмент** (кейсы без `PEFILE_BIN`) запускают настоящий `pefile`
  по бинарной фикстуре `fixtures/sample.dll` и проверяют контракт: имена полей,
  имена архитектуры и флагов, точный состав и порядок таблиц секций и импортов,
  а также настоящие ветки `not_pe` на обрезанном PE и на обычном тексте;
- **мок** (`mock_pefile.py`) проверяет ветки отказа, которых настоящий донор не
  умеет: упасть на конкретном входе, отдать битый JSON, лишние поля, неверные
  типы, зависнуть. Он проверяет разбор ответа и коды ошибок, но **не**
  проверяет, что донор ведёт себя так же, — поэтому группу 1 не заменяет.

Ограничение матчеров `plugin.test.yaml` стоит знать: там есть `contains`,
`equals`, `type`, `present`, но **нет матчера «поля нет»**. Поэтому кейс
«донор отдаёт лишние поля (pdb_path/imphash/timestamp) → наружу не уходят»
проверяет, что известные поля разобрались верно и что `file` остался тем, что
дал оператор; отсутствие `pdb_path` в выводе видно только глазами по
распечатке репорта плагина. Зелёный тест этого не заменяет.

## Фикстуры

`fixtures/sample.dll` — настоящий PE, собранный из `fixtures/sample.c`:

```
x86_64-w64-mingw32-gcc -shared -O1 -Wl,--no-insert-timestamp \
    -o fixtures/sample.dll fixtures/sample.c
```

Исходник лежит рядом с бинарником, чтобы файл можно было пересобрать и
сверить, а не принимать на веру. `--no-insert-timestamp` нужен для
повторяемости: без него линкер пишет в COFF-заголовок время сборки, и два
прогона подряд дают разные байты.

- `sample.dll` (45803 байта): 18 секций, 6 импортируемых DLL, 28 символов,
  `IMAGE_FILE_MACHINE_AMD64`. Есть и секции с длинными именами по ссылке
  (`/4`, `/14`, …), и `.bss` с нулевым размером на диске.
- `truncated.dll` — первые 200 байт того же файла. Настоящий `pefile`
  отвечает на него `PEFormatError('No Optional Header found, invalid PE32 or
  PE32+ file.')`, и это проверяет ветку формата без мока.
- `sample.c` — обычный текст, на который настоящий `pefile` отвечает
  `PEFormatError('DOS Header magic not found.')`.

Фикстуры передаются относительными путями: подпроцесс плагина стартует в
каталоге плагина, абсолютный путь в `plugin.test.yaml` был бы привязан к
машине.
