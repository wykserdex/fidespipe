# PROTOCOL v0.2 — контракт между ядром и плагинами

Это единственный документ, который нужен автору плагина. Заморожен перпендикулярно коду ядра: ядро может быть переписано на другом языке, протокол не меняется.

## 1. Модель исполнения

Плагин — любой исполняемый файл или скрипт (`runtime.type: python | binary | ...`).
Ядро запускает плагин **отдельным процессом** на каждый шаг цепочки:

- **stdin** — JSON-объект со входом (собран ядром строго по секции `input` манифеста)
- **stdout** — ровно один JSON-объект с результатом (никакого постороннего вывода на stdout!)
- **stderr** — свободные логи, ядро складывает их в журнал прогона
- **exit code** — класс результата (см. §3)
- **cwd процесса** — **директория самого плагина**, не корень проекта. Относительные пути
  (`format: file_ref`) плагину приходят «как есть»: `testdata/x` читается от его папки.
  Ядро с v0.2+ предупреждает ⚠ до запуска, если относительный file_ref не резолвится
  от директории плагина (и подсказывает, если такой путь есть от корня проекта).

## 2. Конверт ответа

Успех (exit 0):
```json
{ "status": "ok", "output": { "syntax": true, "mx": ["mx.yandex.ru"] } }
```

Доменная ошибка (exit 1) — плагин отработал штатно, но результат отрицательный:
```json
{ "status": "error",
  "error": { "code": "bad_syntax", "message": "не похоже на email", "retryable": false } }
```

`retryable: true` — просьба плагина к ядру повторить (rate-limit, временный сбой сети). Решение — у ядра (политика шага).

## 3. Exit codes

| code | класс | поведение ядра |
|---|---|---|
| 0 | успех | `output` проходит enforce по контракту, пишется в `steps.<step_id>` |
| 1 | доменная ошибка | применяется `on_error` шага: `stop` / `skip` / `retry` |
| ≥2, таймаут, невалидный stdout | **платформенная ошибка** | всегда остановка рана. Политикой не переопределяется |

- На exit ≥2 ядро парсит конверт, если он есть: `error.code` сохраняется как `platform:<code>` (fallback `crash`), `Platform=true` — ран стопится, но триаж возможен (v9, фидбек внешнего автора №4). До v9 код всегда был `crash` и конверт выбрасывался.

**Граница ответственности:** плагин *сообщает* об ошибке; судьбу цепочки решает конфиг пайплайна. Механизма «плагин стопит цепочку сам» не существует.

## 4. Shared Context

```json
{
  "input": { "emails": ["a@x.ru"], "item": "a@x.ru" },
  "steps": { "syntax": { "syntax": true, "mx": [] } }
}
```

- Плагин видит **только свой вход**: ядро собирает stdin-JSON из путей `input.*` / `steps.*`, перечисленных в манифесте. Весь контекст плагину недоступен.
- `format` — подтип **строк** (`text | email | url | ip | file_ref`); на портах других типов (`array`, `object`, …) `format` запрещён и отклоняется `plugin validate`: форму покрывает `type`, состав элементов плагин проверяет сам в рантайме.
- Плагин пишет **только в свой неймспейс** `steps.<step_id>` (по id *шага*, не плагина — один плагин в цепочке дважды не конфликтует).
- Контекст append-only в рамках прогона: ядро не перезаписывает чужие неймспейсы. Правки человека в `human_gate` пишутся под неймспейсом гейта, источник не затирается.

## 5. Контракт выхода (enforce)

- Поле, **не объявленное** в `output` манифеста, в контекст не попадает (событие `contract_warning` в журнале).
- Объявленное, но **не возвращённое** обязательное поле — нарушение контракта → платформенная ошибка, остановка рана.

## 6. Политики ошибок и scope

```yaml
on_error: stop | skip | retry
retry: { attempts: 3, delay: 5s, backoff: fixed|exponential }
timeout: 30s   # дефолт 60s, максимум 30m
```

- retry повторяет: таймауты и доменные ошибки с `retryable: true`. Остальное — сразу на политику.
- Исчерпанный retry = `stop`.
- **Exit-код `fidespipe pipeline run`:** `0` — ран дошёл до конца (per-item итоги в журнале); `1` — рановая неудача: платформенная ошибка или, в одиночном режиме (без foreach), stop/reject; `2` — usage/ошибка парсинга. CI читает exit-код, аналитик читает журнал.

- **Scope stop:** в обычном пайплайне — остановка рана. В режиме `foreach` (батч по списку) — остановка цепочки **только для текущего элемента**: элемент помечается `item_aborted`, ран продолжается со следующего. Одна битая строка не убивает список из 10 000.
- **Skip-безопасность (статическая):** если шаг `skip`-able, все потребители его выходов обязаны объявить эти входы `optional: true` в манифесте. Проверяется до запуска (`fidespipe pipeline validate`).

## 7. human_gate (встроенная нода ядра, не плагин)

```yaml
- id: review
  plugin: core/human_gate
  form:
    - { field: steps.syntax.mx, editable: false }
    - { field: steps.draft.text, editable: true, type: string }
  actions: [accept, reject]
  on_reject: stop        # stop | continue
```

- Карточка генерируется из типов полей; `editable` поля можно править; правка валидируется по объявленному типу поля.
- **Материализация на accept:** гейт записывает все поля формы под своим неймспейсом `steps.<gate_id>.<поле>` — с правками, если были, исходными значениями, если нет. Downstream-шаги читают **всегда из неймспейса гейта**, а не из источника — так «одобренное человеком» становится явными данными контекста, а источник остаётся нетронутым для аудита.
- **Коллизия basename (v9, фикс внешнего автора №4):** два поля `steps.before.file_count` и `steps.after.file_count` раньше затирали друг друга (basename `file_count`). Теперь при коллизии ключ = `<step_id>_<basename>` (напр. `before_file_count`, `after_file_count`) — данные сохраняются. Валидатор предупреждает о коллизии и подсказывает какие ключи будут в контексте. Без коллизии — старый flat-ключ.
- `reject` → политика `on_reject`.
- CLI-версия работает уже сейчас; GUI-версия использует тот же журнальный протокол.

## 7a. Встроенные модули (`core/*`)

Namespace `core/` — закрытый реестр доверенного кода, который исполняется **в процессе ядра**: без `runtime`, без subprocess, без `plugin.yaml` на диске и без песочницы. Такой модуль объявляет входы и выходы, проходит тот же контракт выхода и ту же политику `on_error`, что и внешний плагин, — отличается только способ исполнения.

| Модуль | Вход | Выход | Назначение |
|---|---|---|---|
| `core/human_gate` | нет | значения не даёт (решение человека) | шлюз: ждёт accept/reject, материализует форму в `steps.<id>.*` |
| `core/text_stats` | `text: string` | `lines`, `words`, `unique_words` (number), `longest_word` (string) | метрики текста; эквивалент community-плагина `text_analyzer` |

Правила namespace:

- Список **закрыт**. `core/<что-то ещё>` отвергается валидатором как неизвестный встроенный модуль, а не ищется на диске.
- Контракт встроенного модуля **не может быть пустым**: пустые `input`/`output` означали бы, что типы выхода не проверяются, а `bind` — не проверяется по портам.
- `permissions` встроенного модуля всегда пусты: он доверенный код в процессе ядра, ему не нужны ни сеть, ни файлы, ни секреты, и declare-now-проверки на нём не срабатывают.
- Расширять список можно только для **узких чистых** преобразований. Встроенный модуль с доступом к файлам или сети размывает границу «всё внешнее исполняется в песочнице» и поэтому не предусмотрен.

Зачем они нужны: до их появления единственным встроенным модулем был `human_gate`, то есть встроенной **полезной** функции не было. Любая осмысленная цепочка требовала внешнего плагина, а значит клона репозитория и Python в `PATH`. `core/text_stats` вместе с командой `fidespipe demo` делает первую цепочку запускаемой на одном бинарнике.

## 8. Журнал прогона

`runs/<timestamp>-<pipeline>/`:
- `pos: [x y]` (v0.25) — сохранённая позиция узла в YAML. При загрузке ядро принимает это поле, а редактор читает его обратно; runtime-полем оно не является.
- `journal.jsonl` — append-only события: `run_start`, `item_start`, `step_start`, `step_end` (exit_code, ms, stderr), `step_skipped`, `gate_wait` (v0.24), `gate_retry` (v0.24), `gate_decision`, `item_aborted`, `item_end`, `run_end`
- `context.json` — снапшот контекста после каждого элемента/шага

Это же — основа `--resume` и GUI-дебаггера.

## 9. Привязка входов (контракт v0.2)

До v0.2 разводка входов (`from:`) жила только в манифесте плагина — два вызова одного
плагина в цепочке были невозможны. В v0.2 пайплайн может перекрыть привязку шагом:

```yaml
- id: refine
  plugin: plugins/llm_gemini      # тот же плагин, что в шаге draft
  bind:                           # перекрывает from манифеста для этих портов
    prompt: steps.review.text
    system: input.refine_system
```

Правила:

1. Источник порта = `bind` шага, если задан; иначе — `from` манифеста; если нет ни того, ни другого — **ошибка статической валидации** («нет привязки»), кроме `optional: true` портов — для них отсутствие привязки = warning «optional — допустимо» (v9, фикс внешнего автора №4, инверсия раньше ломала смысл v0.2).
2. `bind` на несуществующий порт — ошибка валидации (защита от опечаток).
3. Привязанные пути проходят полные статические проверки: существование источника, совместимость типов/форматов, skip-безопасность — со стороны данных всё то же самое, поменялось лишь то, **кто назначает разводку**.
4. `bind` к `core/human_gate` не применим (его контракт — `form`).
5. Обратная совместимость: пайплайны `format_version: "0.1"` работают без изменений; манифесты с `from` — это дефолты, не обязательства. Манифест без `from` легален со смыслом «привязку обязан дать пайплайн». `format_version` с опечаткой (напр. "2.0") теперь — ошибка, а не warning+OK (v9, важно для CI).
6. Pipeline-`foreach` принимает `input.*` (батч на входных данных) и `steps.<id>.<field>` (батч после pre-фазы, v0.12). `foreach` на шаге — §12.2.

## 10. Сознательно НЕ входит в протокол сейчас

- ревалидация правок гейта по контракту *следующего* шага (сейчас — по типу поля в form)
- изоляция `permissions` (песочница/OS-level) — сейчас declare-now: §11 (уровень L1)
- секреты: значения — env-переменные; имена — `secrets:` пайплайна + `permissions.secrets` манифеста (v0.16/v0.17, §11); `secret://`-ссылки и keyring — нет

`--resume`, `when`, `foreach` и `parallel_group` реализованы и описаны в §12; CLI, API и MCP используют одну pre-run валидацию.

Одна pre-run **валидация** — не значит «одинаковые pre-run отказы». У MCP сверх неё есть отказ, которого нет у CLI и API: `E_GATE_REQUIRED`, если первый шаг с опасными capabilities (сеть, запись на диск, чтение секретов — §11) идёт без `core/human_gate` перед собой. Причина именно в MCP: там инициатором запуска может быть агент, и решение человека должно предшествовать опасному шагу, а не следовать за ним. Подробности и границы правила — [ERRORS.md](ERRORS.md).

## 11. permissions: declare-now (v0.17)

`permissions` манифеста — **контракт + аудит**, не песочница: оркестратор не
держит subprocess в изоляции (чистый Go, без контейнеров). Честное исполнение — три уровня:

1. **Декларация — условие попадания в реестр.** `fidespipe registry validate`
   (CI-гейт): манифест с `id` = имени в реестре, `plugin.test.yaml` с зелёными
   тестами и валидными декларациями `permissions` (пустое поле означает
   отсутствие заявленной capability). Запись в registry.yaml без конформности —
   не запись, а долг.
2. **Сеть запрещена по умолчанию.** Плагин заявил `permissions.network`, а
   пайплайн не записал `network: allow` — **ошибка до любого эффекта** (и
   валидатор, и раннер независимо). Поле `network: deny` и незаполненное поле
   означают одно и то же: пустое поле — это отсутствие решения, а не
   разрешение. Честный сетевой плагин не спрячется за «пайплайн не просил».
   Обратная сторона: `network: allow` со списком `host:port` — тоже ошибка
   (`E_NETWORK_NOT_ENFORCEABLE`), потому что точечный фильтр не реализован и
   полный доступ вместо списка хостов выдавать нельзя.
3. **`FIDESPIPE_NETWORK` в env subprocess** — раннер передаёт каждому шагу `allow`/`deny`,
   причём `deny` приходит и при незаполненном поле; добропорядочный плагин
   читает переменную и отказывается от сетевых вызовов в deny. Заявленная сеть
   пишется в журнал (`step_start.network_declared`) —
   аудит-след виден в `runs show`.

Кросс-проверка `secrets`: валидатор сверяет `secrets:` пайплайна (имена env)
с `permissions.secrets` манифестов шагов. Ключ объявлен пайплайном, но ни один
плагин его не заявляет — warning; плагину нужен ключ, но пайплайн его не
объявляет — warning (при запуске его может не быть в env).

**Сознательно вне** на этом уровне: OS-изоляция сети, `secret://`-ссылки,
keyring. Декларация проверяется и аудируется — исполнение на честности плагина.

## 12. Управляющий поток на уровне шага (v0.20)

Три механизма, все — на уровне шага, все видны в журнале и в `pipeline plan`
(аннотации `when` / `foreach` / `parallel_group` в DAG).

### 12.1 `when` — условие шага

```yaml
- id: freq
  plugin: plugins/community/word_freq
  when: { path: steps.stats.words, op: gte, value: 10 }
```

- Строковый формат `when: steps.stats.words` — сахар: шаг выполняется, если
  значение **истинно** (bool; непустая строка; непустой массив/объект; ненулевое число).
- Операторы: `truthy`, `exists`, `missing`, `eq`, `neq`, `gt`, `gte`, `lt`,
  `lte`, `contains` (подстрока / элемент массива). `op` по умолчанию — `eq`.
- Условие ложно → шаг **пропущен**: журнал `step_skipped` (reason=when), выход
  не пишется. Порт, читающий пропущенный шаг, = «нет привязки» — ошибка:
  условие — это не гарантия данных.
- Условие не оценивается (например, `gt` по строке) → **ошибка рана**: это
  нарушение контракта, а не данные.
- Честные числа: int из YAML = float64 из JSON; «нет пути» = null
  (`missing: true`, `eq: null`).

### 12.2 `foreach` на шаге

```yaml
- id: freqs
  plugin: plugins/community/word_freq
  foreach: input.texts        # массив из input.* или steps.<id>.<field> (шаг уже выполнен)
  foreach_item: text          # имя переменной в input.* (по умолчанию item)
```

- Шаг выполняется по каждому элементу; `input.<foreach_item>` перезаписывается
  на итерацию.
- `steps.<id>` — выход **последней** итерации; `steps.<id>_all` — массив всех
  выходов (пропущенные итерации в массив не входят).
- Отличие от pipeline-`foreach`: «элемента» здесь нет — `on_error=stop`
  останавливает **весь ран**; `skip`/`retry` — как обычно.
- Совмещается с pipeline-`foreach` (вложенные циклы): в пер-элементный
  агрегат попадает `steps.<id>_all` внутреннего шага.
- Ошибки валидации: `foreach` + `after_foreach`, `foreach` + `parallel_group`,
  `foreach` у `human_gate`, путь не из `input.*`/`steps.*`, источник из
  ещё не выполненного шага.

### 12.3 `parallel_group` — параллельные ветки

```yaml
- id: words
  plugin: plugins/community/word_freq
  parallel_group: analyze
- id: flat
  plugin: plugins/community/json_flatten
  parallel_group: analyze
```

- **Смежные** шаги с одинаковым именем группы исполняются параллельно; барьер
  ждёт все ветки до следующего шага.
- Каждая ветка работает на **копии контекста**; после барьера выходы сливаются
  в общий контекст в порядке списка (детерминизм — кто быстрее, не влияет).
- `on_error=stop` или платформенная ошибка в ветке → **ран остановлен**
  (барьер не терпит половин). `skip` → выхода ветки нет (status `skipped`
  в `parallel_end`).
- `human_gate` в группе запрещён: гейты сериализуют терминал.
- Журнал: `parallel_start` (group, steps) / `parallel_end` (group, statuses,
  duration_ms); события веток переплетены по времени.
