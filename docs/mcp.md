# fidespipe mcp — контрактный исполнитель для LLM-агентов

Агент предлагает план → fidespipe проверяет до запуска → опасные шаги ждут решения
человека → fidespipe исполняет и ведёт журнал. Шаги без заявленных опасных прав
(сеть, запись на диск, чтение секретов) выполняются без гейта — иначе правило
запрещало бы агенту полезную работу.

Транспорт: stdio JSON-RPC 2.0, по одному сообщению на строку. Своя минимальная
реализация без зависимостей: `initialize`, `notifications/initialized`,
`notifications/cancelled`, `tools/list`, `tools/call`, `ping`, плюс запросы
сервера клиенту (`elicitation/create`). Батч-массивом считается строка,
начинающаяся с `[`; ответ приходит массивом в порядке запросов.

### Ревизия протокола и поведение транспорта

| Что | Как |
|---|---|
| Поддерживаемые ревизии | `2025-06-18` (по умолчанию) и `2024-11-05` |
| Клиент просит поддерживаемую | возвращается она же |
| Клиент просит другую | возвращается самая новая из поддерживаемых, а не самая старая: понижение не должно выглядеть как согласие |
| Ревизия 2026-07-28 | не заявлена сознательно: она заменила хендшейк `initialize` на `server/discover` и `_meta` в каждом запросе — объявлять её, не реализовав этот путь, было бы ложью |
| Батч-массивы | принимаются (`[ {...}, {...} ]`), ответ — массив в порядке запросов; в `2025-06-18` их уже нет, в `2024-11-05` они обязательны |
| Битая строка | ответ `-32700 Parse error` с `id: null`, сессия продолжается |
| Пустой батч | `-32600 Invalid Request` |
| Неизвестный инструмент | `-32602` («Unknown tool: X») — инструмент ищется в `tools/call`, а не метод JSON-RPC |
| Нотификации | принимаются любые; ответа не получают (`notifications/*`) |

`notifications/cancelled` **действует**: нотификация с `requestId`, равным id
вызова `run_pipeline` или `exec_plugin`, отменяет соответствующую работу — ран
или запущенный процесс. Это то, что посылает клиент, когда пользователь нажал
Esc или запрос оборвался. Без этого отменённый запрос продолжал держать
единственный слот рана, и агент до таймаута получал `E_RUN_BUSY`.

Одно отклонение от буквы спеки, названное явно. Спека советует игнорировать
отмену запроса, на который уже отправлен ответ. У нас запрос и ран кончаются в
разные моменты: `run_pipeline` отвечает `waiting_human`, а ран продолжает жить,
и клиент, у которого человек нажал Esc уже после ответа, об этом узнаёт только
нотификацией. Поэтому связь «id запроса → ран» хранится, **пока жив ран**, и
поздняя отмена находит его. Риск: клиент, переиспользующий id, может отменить
чужой ран — но живых ранов не больше одного (`E_RUN_BUSY`), а совпасть должны
и id, и незавершённый ран, поэтому цена ошибки ниже цены занятого слота.

`tools/list` отдаёт аннотации (`readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint`) — по ним хост решает, показывать ли человеку
подтверждение. Спека велит клиентам считать аннотации недоверенными, но без них
`list_plugins` (чтение каталога) и `run_pipeline` (запуск чужого кода) выглядят
для хоста одинаково.

### Структурированный результат (`structuredContent`, `outputSchema`)

Каждый инструмент объявляет `outputSchema`, и при успешном вызове результат
приходит дважды: текстом (для совместимости, как требует спека) и объектом в
`structuredContent` — клиенту не нужно разбирать строку.

Что здесь честно ограничено:

- Схемы описывают только инвариант: имена и типы полей, которые есть всегда.
  `required` не ставится там, где поле появляется не при каждом исходе —
  `run_pipeline` при отказе валидации возвращает `{ok, issues}` без `run_id`.
- `structuredContent` не приходит при `isError` и при RPC-ошибке: спека требует
  соответствия объявленной схеме, а у ошибки исполнения своя форма.
- Список замечаний — всегда массив (`[]`, а не `null`), иначе типизированный
  клиент получал бы нарушение собственной схемы сервера.

### Прогресс долгих вызовов (`notifications/progress`)

`run_pipeline` умеет ждать до 300 секунд, `exec_plugin` — до 300. Чтобы клиент с
таймаутом на `tools/call` не обрывал вызов раньше, чем ран дойдёт до гейта,
сервер шлёт прогресс **раз в секунду** во время ожидания и одну нотификацию
перед запуском плагина.

Прогресс уходит, только если клиент дал `_meta.progressToken` в запросе: без
токена клиент не сопоставит нотификацию с вызовом, и спека это запрещает. Нет
токена — сервер молчит, а не выдумывает свой идентификатор.

## Запуск

```bash
go build -o fidespipe ./cmd/fidespipe
fidespipe mcp --plugins /abs/path/plugins --workdir /abs/path/project
```

- `--plugins <dir>` — repeatable, корни плагинов.
- `--workdir <dir>` — корень `path` пайплайнов и `file_ref`.
- Это проверка ссылок и путей, не OS-песочница: процессы плагинов наследуют права пользователя.
- Абсолютные пути и `..` вне корней → `E_PLUGIN_OUTSIDE_ROOT`.
- `secrets` — только имена, значений в ответах нет.
- Один ран за раз: занят → `E_RUN_BUSY` с id текущего рана.
- `--runs-dir <dir>` — каталог ранов (по умолчанию `<workdir>/var/runs`).
- Флаги принимают и `--x v`, и `--x=v`.
- `os.Stdout`/`stdin` изолированы: JSON-RPC — только в proto-stdout,
  весь шум раннера/гейта — в stderr. `StdinUI` в MCP запрещён (`E_NO_GATE_UI`).

## Инструменты

| Tool | Вход | Выход |
|---|---|---|
| `list_plugins` | `filter?` | id, version, description, порты, permissions |
| `describe_plugin` | `id` | манифест целиком |
| `validate_pipeline` | `yaml` \| `path` | `{ok, issues[]}` — `ok:false` норма, не `isError` |
| `plan_pipeline` | `yaml` \| `path` | DAG + issues |
| `run_pipeline` | `yaml`\|`path`, `wait_seconds?` (0..300) | сначала validate, затем `{run_id, status: running\|waiting_human\|done\|failed\|cancelled}`; сверху отказ `E_GATE_REQUIRED`, если первый опасный шаг идёт без `core/human_gate` |
| `get_run` | `run_id`, `since?` | статус, stats, новые события, выходы (~20KB), `pending_gate{step,form,actions}` без токена; события окном: `total`, `first`, `next` (курсор догрузки), `truncated` при обрезании по потолку ответа |
| `cancel_run` | `run_id` | `{status:"cancelling"}`; затем `get_run` → `cancelled` (`E_RUN_DONE`, если ран уже завершён) |
| `exec_plugin` | `id`, `input?` | результат плагина (`stdout`, `exit_code`, `err_code?`); **выключен по умолчанию**, см. ниже |

## Гейты: как человек одобряет шаг агента

`fidespipe mcp` поднимает **консоль гейтов** — HTTP на `127.0.0.1:<случайный порт>`
(`--gui-listen=host:port`) с сессией человека. Вход в консоль — по
**одноразовому коду**: cookie сессии живёт только в памяти процесса, а код
обменивается на неё один раз.

1. Ран агента доходит до `human_gate` → `get_run` отдаёт `waiting_human` +
   `pending_gate{step,form,actions}`.
2. fidespipe открывает браузер человека на `/?run=<id>&c=<код>` (один раз на
   гейт). Код обменивается на HttpOnly cookie, после чего redirect без `c`.
   С `--no-open` или `--print-link` ссылка с кодом печатается в stderr
   MCP-процесса (лог клиента): там она живёт 10 минут и обменивается один раз.
3. Агент в `hint` видит только адрес `/?run=<id>` **без кода**. Его
   `curl …/gate` → `401 E_SESSION_REQUIRED` (так же, как любой другой GET
   под `/api/*` — чтение журналов и входов шагов тоже закрыто).
4. Человек правит форму, жмёт accept или reject. В журнал пишется
   `gate_decision{source:"gui", session:<хэш>}`, ран продолжается.

`--gui-listen` на не-loopback адресе отвергается: внешний доступ к решениям
человека должен быть сказан явно (`fidespipe gui --allow-remote --public-host=…`).

Модель угроз: код/cookie защищают от агента и любых процессов, которые умеют
только слать HTTP на локальный порт. Они не защищают от процесса, который
читает stderr MCP-клиента, экран или профиль браузера того же пользователя.
Для этого нужна отдельная ОС-учётка или `fidespipe approve` в TTY: команда лишь
подтверждает намерение человека и показывает защищённый API-вызов; окончательное
решение всё равно отправляет человек из GUI/API с сессией.

`--no-gui`: консоли нет. Пайплайн с шагом-гейтом отклоняется **до старта**
(`E_NO_HUMAN_CHANNEL`), чтобы ран не висел вечно в `waiting_human` — если не
включён гейт через elicitation (ниже).

## Гейт через диалог клиента (`elicitation/create`)

Ревизия 2025-06-18 даёт серверу стандартный способ спросить человека через
интерфейс клиента. С флагом `--gate-elicitation` fidespipe показывает форму гейта
диалогом MCP-клиента, а не только в собственной консоли:

```bash
fidespipe mcp --plugins /abs/path/plugins --workdir /abs/project --gate-elicitation
```

Условия, при которых гейт идёт этим путём (все три обязательны):

1. `--gate-elicitation` — оператор разрешил канал;
2. клиент объявил `capabilities.elicitation` в `initialize`;
3. клиент отвечает на запрос.

Не выполнено хоть одно — работает консоль, а без консоли ран отклоняется
(`E_NO_HUMAN_CHANNEL`), как и раньше.

Почему флаг, а не «включено, если клиент умеет». fidespipe **не может проверить,
что за клиентом сидит человек**: автономный хост вправе ответить сам. Доверие
каналу выдаёт оператор, который знает свой клиент, — а имя решения в журнале
остаётся честным: `gate_decision{source:"mcp_elicitation"}` отличается и от
`gui`, и от `terminal`, и от `agent_auto`.

Как ведёт себя канал:

| Ответ клиента | Решение | Почему так |
|---|---|---|
| `accept` | `accept` + правки | значения приходят строками и разбираются как JSON (`"42"` → `42`) |
| `decline` | `reject` | семантику `on_reject` решает пайплайн, а не транспорт |
| `cancel` (диалог закрыли) | стоп | та же семантика, что у EOF: закрытый ввод — не «accept» |
| ошибка/таймаут (30 мин) | консоль, если есть; иначе стоп | человек не ответил — решение не выдумывается |
| действие не из списка | retry-цикл гейта (≤5), затем стоп | как в терминале и в консоли |

Чего этот путь **не** делает:

- не отдаёт агенту инструмент одобрения: агенту по-прежнему нечем одобрить
  гейт, он лишь передаёт запрос человека, а показывать ли диалог — решает хост;
- не показывает вложенные структуры: схема elicitation плоская (только
  примитивы), поэтому поля формы отображаются как строки;
- не заменяет консоль: консоль остаётся и как основной путь без флага, и как
  фолбэк, если клиент не ответил.

Решения гейтов через MCP **агенту недоступны никогда**: у агента нет инструмента
одобрения, он лишь передаёт запрос человека. `get_run` в `waiting_human`
возвращает «попросите пользователя одобрить шаг X в окне fidespipe» (а с
`--gate-elicitation` человек видит диалог прямо в клиенте — см. ниже).
Для раннов из MCP `AllowAutoApprove=false` всегда, независимо от YAML.

## Гейт обязателен перед опасным шагом (`E_GATE_REQUIRED`)

Отсутствие инструмента одобрения — половина контракта. Вторая половина: агент не
может выкинуть гейт, чтобы одобрение не понадобилось. `run_pipeline` отказывает
до старта рана, если **первый** шаг с capabilities «сеть / запись на диск /
чтение секретов» (по `permissions` манифеста) идёт без `core/human_gate` перед
собой. Гейт после такого шага не защищает: человек увидел бы результат, а не
намерение, поэтому отказ прямо говорит, что гейт стоит слишком поздно.
Опасных шагов нет — гейт не требуется.

Отказ: RPC-ошибка, `Data = {"code":"E_GATE_REQUIRED","step":…,"plugin":…}`;
текст `message` называет права шага и что делать. Подробности, границы правила и
операторский обход — [protocol/v0.2/ERRORS.md](../protocol/v0.2/ERRORS.md).

| Флаг | Что разрешает |
|---|---|
| `--allow-unapproved-runs` | ран с опасным шагом без гейта; предупреждение в stderr при старте + строка в `<runs-dir>/gate-bypass.jsonl` на каждый обход; не записалась — отказ до старта |

Правило ловит **объявленное** намерение, а не поведение кода: `permissions` —
декларация, не песочница (см. [SECURITY.md](../SECURITY.md)). Плагин, солгавший
в манифесте, этим правилом не ловится — его ловит `sandbox: untrusted` и
изолятор ОС.

Коды ошибок — `protocol/v0.2/ERRORS.md` (публичный контракт).

## `exec_plugin`: запуск плагина агентом

Отдельный инструмент: агент исполняет плагин напрямую, без пайплайна и без гейта.
Выключен по умолчанию, включается флагом при запуске:

```bash
fidespipe mcp --plugins /abs/path/plugins --workdir /abs/path/project --allow-agent-exec
```

| Флаг | Что разрешает |
|---|---|
| `--allow-agent-exec` | вообще вызовы `exec_plugin` (без него `E_AGENT_EXEC_DENIED`) |
| `--allow-untrusted-plugins` | плагины агента и untrusted-манифесты идут в изолятор; без флага — `E_AGENT_PLUGIN_UNTRUSTED` |
| `--deny-untrusted-plugins` | запретить untrusted при `--allow-agent-exec`, оставив доверенные |

**Гейт не запрашивается, и это осознанно.** У инструмента нет шага, где человек
ответил бы «нет»: агент звонит, политика решает. Спросить человека нельзя
технически — агент не человек, а `waiting_human` на этом инструменте был бы
вечным ожиданием. Плагин, написанный агентом, распознаётся по пути
(`plugins/agent-plugins/...`) и по умолчанию изолируется, а не выполняется
с правами пользователя.

**Границы `exec_plugin`.** Требование `E_GATE_REQUIRED` на инструмент не
распространяется: состояния «ждёт человека» у него нет, и ждать некому. Поэтому
запрещено то, что гейт защищал бы — `exec_plugin` отказывает плагинам с
объявленными правами, код `E_AGENT_EXEC_CAPABILITIES`. Сеть отклонялась и до
этого (`E_NETWORK_DENIED`), так что под правило попадают запись на диск, чтение
секретов и непрочитанный манифест. Такой плагин запускается только через
`run_pipeline` с `core/human_gate` перед опасным шагом.

Чего правило не делает: оно читает декларацию в манифесте, а не поведение кода.
Плагин, заявивший `filesystem: none`, всё равно может писать правами
пользователя. Против врущего манифеста работает другое — изолятор для
недоверенных плагинов и allow-list доверия по хэшу содержимого.

Остаётся нерешённым другое: у инструмента нет способа показать человеку план
до запуска. Сужение до безопасных capabilities закрывает класс «запись и
секреты в обход гейта», но не даёт человеку увидеть, что именно собирается
запустить агент.

Плагин считается «написанным агентом», если **любая компонента его пути**
равна `agent-plugins` (`internal/plugin/trust.go:52`). Сравнение идёт по
компонентам, а не по подстроке и с учётом регистра на Windows: иначе
`Agent-Plugins\` признавался бы обычным каталогом, то есть доверенным, а
`mailer-agent-plugins/` — наоборот, агентским. Ошибка всегда в сторону
песочницы: лишняя песочница дешевле обхода доверия.

Каждый запуск пишет в `<runs-dir>/agent-exec.jsonl` две строки, связанные
`exec_id`: намерение — **до** запуска, результат — после (формат —
`protocol/v0.2/ERRORS.md`). Если намерение не записалось, плагин не запускается
вовсе: `E_AGENT_EXEC_AUDIT`. Если не записался результат — код уже отработал,
агент результата не получает, а намерение в журнале остаётся. Одновременных
запусков не больше 4, дальше `E_AGENT_EXEC_BUSY` — не очередь.
