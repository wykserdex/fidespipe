# Свой плагин за 15 минут (для авторов, без подглядывания в чужой код)

Выверено на 8 реальных граблях внешних тестеров (M5_FEEDBACK.md).
Путь: скелет → своя логика → контракт-тесты → своя цепочка. SDK не существует —
плагин это обычный скрипт.

## 0. Бинарник (1 мин)

Release-архив → `wedra-<os>-<arch>[.exe]` → `chmod +x`. Проверка: `./wedra --help`.
Все команды ниже — `wedra` (один бинарник) или `wedra.exe` под Windows.

## 1. Скелет (2 мин)

```bash
wedra plugin create plugins/мой_плагин --author ТЫ --description "Что делает" --example array
#   --author/--description: чтобы не было TODO в манифесте
#   --example string (по умолчанию) | array — форма входа
```

Гарантия генератора: скелет сразу валиден и зелёный:

```bash
wedra plugin validate plugins/мой_плагин   # OK
wedra plugin test plugins/мой_плагин       # все тесты passed
```

## 2. Контракт за 90 секунд (это весь «SDK»)

- **stdin** ← JSON со входом (ядро собирает его из секции `input` манифеста).
- **stdout** → РОВНО один JSON: `{"status":"ok","output":{...}}` (exit 0, успех)
  или `{"status":"error","error":{"code","message","retryable"}}` (exit 1 — доменная
  ошибка: плагин отработал, но результат отрицательный). Любой мусор на stdout /
  падение ≥2 — платформенная ошибка, стопит ран.
- **stderr** — любые логи, попадут в журнал рана (`runs/<id>/journal.jsonl`).
- Судьбу цепочки решает YAML пайплайна (`on_error: stop|skip|retry`), не плагин.
- Шпаргалка типов лежит прямо в шапке сгенерированного `plugin.yaml`:
  `type: string|number|boolean|array|object`, `format` (только для строк):
  `text|email|url|ip|file_ref`.
- **`permissions` — честно (declare-now)**: `network: [{host, port}]` —
  каждый сетевой вызов (пусто = сети не будет; пайплайн с `network: deny`
  запрещает такие плагины запуском), `secrets: [ENV_KEY]` — каждый env-ключ,
  который читаешь. Валидатор сверяет с `secrets:` пайплайна, заявленная сеть —
  в аудите журнала. Не «декларация для галочки»: это контракт.
- `runtime.requires` — декларация pip-зависимостей в формате
  `package==version`. `install` ставит их сам, когда ставит плагин; рядом с
  manifest обязателен `requirements.lock` с теми же exact pins.
  Для воспроизводимого plugin проверяй lock-файл и окружение contract-тестами.
- `runtime.donor` — рецепт донора, которого нет на PyPI: Go-программа,
  готовый бинарь или скрипт. Ставится вместе с плагином, а отдельная строка
  «поставь руками» больше не нужна:

  ```yaml
  runtime:
    type: python
    entry: main.py
    requires: []
    donor:
      kind: go          # go | binary | script
      name: gospider    # как плагин будет звать донора
      version: v1.1.6
      module: github.com/jaeles-project/gospider
      bin_env: GOSPIDER_BIN   # переменная, в которую ядро положит путь
  ```

  Три вида: `go` (`go install module@version`), `binary` (`url` + `sha256`),
  `script` (`url` + `sha256` + `interpreter`). **Для `binary` и `script` sha256
  обязателен** и сверяется до распаковки: качать исполняемый код из сети, не
  сверив хеш, — это не установка, а закладка. Адрес — только `https`.

  `bin_env` — имя переменной, которую плагин читает. Оно своё у каждого
  плагина (`GOSPIDER_BIN`, `EXIFTOOL_BIN`), и ядро не может его угадать: путь
  к донору кладётся именно в эту переменную. Плагин читает её так:

  ```python
  bin_env = os.environ.get("GOSPIDER_BIN", "gospider").strip()
  bin_env = shutil.which(bin_env) or os.path.abspath(bin_env)
  ```

  Донор ставится **вне каталога плагина** — в `<plugins>/.donors/<id>/`. Это не
  выбора вкуса: доверие выдаётся по хэшу содержимого каталога, и установка
  донора внутрь изменила бы хэш, то есть плагин перестал бы быть доверенным
  ровно в момент установки.

## 3. Своя логика

Правим `main.py` (в шаблоне уже есть `fail()`/`ok()` и чтение stdin).
Правила выживания, заученные тестерами:

1. **Не гадай тип** — guard'ь: вход `type: array`? `isinstance(items, list)` с
   платформенной ошибкой. Статика validate проверяет ПАЙПЛАЙН, в рантайме
   тип твоего входа плагину не гарантирован — контракт проверяй сам.
2. **Относительные пути — от папки плагина**: cwd процесса = директория плагина,
   не корень проекта (ядро с v0.2 предупредит ⚠, если такой путь есть от корня).
3. **Доменная ошибка vs платформенная**: «пользователь дал пустой текст» → exit 1;
   «мне прислали битый JSON» → exit 2. Тестеры ошибались ровно здесь.

## 4. Контракт-тесты — твой цикл разработки

```bash
wedra plugin test plugins/мой_плагин   # гоняет тот же subprocess-протокол, что и ядро
```

В `plugin.test.yaml`: кейсы `input → expect`. Матчеры: литерал (глубокое равенство),
`{ equals: X }`, `{ contains: "..." }` (строка И массив), `{ present: true }`,
`{ type: "array" }`, `{ absent: true }` — «наружу это поле не уходит»
(незадекларированное ядро отбрасывает, объявленное уходит); `env: {...}` —
секреты/mock на время теста; `input_raw` — сырой stdin для тестов битого JSON.
Прогон включает enforce: вернул поле не того типа — тест красный даже если Python
«всё напечатал».

### Живой донор вместо мока: `services`

Если плагин зовёт внешний инструмент, а тот ходит по сети (arjun, dirsearch,
wapiti, wfuzz, xsstrike), тест на моке ничего не проверяет: мок отвечает заранее
придуманным JSON, а настоящий донор против закрытого порта просто пишет
«Skipped» и не создаёт отчёт. Тогда поднимается локальный сервер с фикстурами:

```yaml
services:
  - type: http
    root: fixtures/site        # каталог, который отдаётся (путь от папки плагина)
    base_url: "{{base_url}}"   # имя плейсхолдера, подставляемого в кейсы

tests:
  - name: живой скан по фикстуре
    input: { url: "{{base_url}}", wordlist: "words.txt" }
    expect:
      status: ok
      output: { count: 2 }
```

Что важно знать:

- **сервер один на прогон**: поднимается ДО кейсов на свободном порту, гасится
  после (даже если кейс упал). Печатается строкой `ℹ сервис http: …`.
- **`{{base_url}}` подставляется** в `input` (включая вложенные объекты и
  списки), в `input_raw` и в значения `env`. Неизвестный плейсхолдер `{{...}}` —
  ошибка, а не пустая строка. В `expect` подстановки нет: там порт неизвестен
  заранее, поэтому URL проверяют матчерами (`{ type: string }`, `{ contains: "/admin" }`).
- **только `type: http`**. Любой другой тип — внятная ошибка, а не пропуск.
  Поля с произвольной командой нет и не будет: это отдельная задача.
- **`root` проверяется до кейсов**: нет каталога (или это файл) — прогон
  останавливается с объяснением.
- **сеть плагина не расширяется**: сервис не добавляет прокси-переменных и не
  правит `permissions`. Loopback и так доступен каталогу, который оператор сам
  назвал в `wedra plugin test`; сервер слушает только `127.0.0.1` и наружу не
  публикуется.
- **файл без `services` работает ровно как раньше**, включая тексты со скобками
  `{{...}}` внутри — подстановка включается только когда сервис объявлен.
- **донор должен быть установлен**: живой кейс честно падает с
  `*_not_installed`, если пакета нет. Для CI ставьте его рядом с `ssl_info` и
  `detect_secrets` (см. `.github/workflows/ci.yml`).

## 5. В цепочку (pipeline, protocol 0.2)

```yaml
format_version: "0.2"
pipeline:
  name: my_first
  input: { text: "привет мир" }
  steps:
    - id: mine
      plugin: plugins/мой_плагин
      # from в манифесте — только дефолт; здесь можно перекрыть:
      # bind: { text: input.text }
      on_error: stop
```

```bash
wedra validate examples/my_first.yaml   # ловит типы/форматы/разводку ДО запуска
wedra run examples/my_first.yaml        # --yes = авто-accept гейтов (CI)
```

Один плагин дважды в цепочке — нормально: второй вызов с другим `bind:`
(см. `examples/llm_same_provider.yaml`, `dir_snapshots.yaml`).

## 6. Грабли, на которые уже наступили (и как их не наступить)

| Грабля | Рецепт |
|---|---|
| `format: json` на `type: array` → взрыв в пайплайне | format — только строкам; массиву хватит `type: array` |
| относительный путь в pipeline → not_found | пути — от папки плагина или абсолютные; смотри ⚠ от run |
| опечатка в `bind:` порту | `validate` перечислит существующие порты |
| «объявил string, вернул int» | enforce скажет это в plugin test сразу |
| плагин читает выход skip-able шага | вход сделай `optional: true`, иначе validate красный |

## 7. Сдать в реестр

Путь плагина в публичный реестр (`registry.yaml` в корне репо):

1. **Зелёные контракт-тесты** — гейт. `wedra plugin test <dir>` — все
   PASS (минимум 3 кейса: happy path, доменная ошибка, битый JSON exit 2;
   реальных ключей в тестах нет — mock-режим, см. LLM-плагины).
2. **Манифест честный**: `id` совпадает с именем в реестре, `permissions`
   заполнены по §2, `author` — ты (ник/имя).
3. **Сдача — любой способ** (по трению):
   - zip папки автору → он делает PR (каталог + запись в registry.yaml);
   - fork + PR в `wykserdex/wedra`: `plugins/community/<name>/` + 4 строки
     записи (`source`, `path`, `version` = тег релиза, `description`);
   - свой репо с тегом → запись в реестре указывает `source` на твой репо
     (полное владение плагином — у тебя).
4. **CI** прогоняет `wedra registry validate`: манифест, id, все
   конформные тесты. Красный = в реестре не окажешься.

После попадания: любой `wedra plugin install <твой_плагин>` — и плагин
у него в `plugins/`, а пресеты тянут его автоматически. Полный цикл приёма (что проверяем и как попадаем в реестр) — в
[CONTRIBUTING.md](../CONTRIBUTING.md#registry-admission).
