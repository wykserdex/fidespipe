# Импорт чужого проекта в плагин

`wedra plugin import` разбирает произвольный Python-проект и создаёт из него
каталог плагина, который проходит гейт. Остальное дописывает человек — в
редакторе плагинов (`/plugins/`) или в текстовом редакторе.

```bash
wedra plugin import ./telegram-outreach          # разобрать и создать
wedra plugin import ./telegram-outreach --plan   # только показать план
```

Каталог плагина по умолчанию — `plugins/<id>`.

Документ описывает прогнанный на живом проекте разбор: что делается
автоматически, что человек обязан решить сам и где проходит граница.

## Команда

```bash
wedra plugin import <каталог-проекта> [<каталог-плагина>] [--id=ИМЯ] [--description=ТЕКСТ] [--plan]
```

`--plan` печатает разбор и план, **ничего не записывая**: посмотреть, что
выйдет из чужого проекта, можно и не создавая каталог. Без `--plan` команда
создаёт плагин, проверяет его манифест и прогоняет стартовые тесты.

## Что происходит

1. `internal/importer.Inspect` читает `pyproject.toml` (или `setup.cfg`) и
   находит: имя и версию проекта, `requires-python`, зависимости, точки входа
   из `[project.scripts]`, раскладку (`src/` или плоская), README.
2. `internal/importer.Plan` строит план: имя плагина, требования, найденные
   точки входа, модуль для `sys.path`, **предупреждения** и **блокеры**.
3. `internal/importer.Generate` пишет каталог: `plugin.yaml`, `main.py`,
   `plugin.test.yaml`, `README.md`. Сгенерированный плагин сразу проходит
   `wedra plugin validate` и даёт зелёные тесты — он не «почти готов»,
   а действительно валиден.

## Что автоматика НЕ делает и почему

**Не разрешает диапазоны версий в пины.** `runtime.requires` принимает только
`package==version`, а большинство проектов пишет `>=2.6,<3.0`. Из диапазона
нельзя получить одну версию, не спросив окружение. Импортёр оставляет такие
требования в `Unresolved` и объявляет блокером, а не угадывает.

**Не выбирает функцию донора автоматически.** Точка входа `[project.scripts]`
почти всегда указывает на CLI — а контракт плагина WEDRA «прими JSON, верни
JSON». Автоматически обернуть CLI было бы выдумкой, поэтому импортёр этого не
делает, а `main.py` останавливается с `donor_not_wired`.

**Не исполняет `setup.py`.** Это чужой исполняемый код. Проект, у которого нет
`pyproject.toml` или `setup.cfg`, отвергается с объяснением.

**Не копирует права.** `permissions` в сгенерированном манифесте пустые. Сеть
не угадывается никогда — это решение человека.

## Прогнанный разбор: telegram-outreach

Проект — https://github.com/wykserdex/otklik (платформа Telegram-аутрича,
Telethon, SQLAlchemy, alembic).

| Что | Значение |
|---|---|
| Имя и версия | `telegram-outreach 0.1.0`, `requires-python >=3.11` |
| Раскладка | `src/` |
| Зависимостей в `pyproject.toml` | 12, все диапазонами |
| Точек входа | 1: `telegram_outreach.main:cli` (CLI) |
| Порт в доменном слое | `MessageBody` — чистая валидация текста |

Скелет от импортёра: `ValidatePluginDir` — без ошибок, `RunPluginTests` — 3/3.

После ручной правки (она же — работа в редакторе плагинов) плагин
`msg_check` получил настоящий вызов и **одну** зависимость вместо двенадцати:

```
requires: [pydantic==2.12.3]
```

Доменный слой проекта тянет только `pydantic`; остальные одиннадцать нужны
боту и базе, а не этому плагину. Это важный вывод: **число зависимостей
плагина не равно числу зависимостей проекта**, и узнать правильное число можно
только посмотрев, что реально импортирует нужная точка входа.

Проверено end-to-end на Windows: `plugin test` — 5/5, настоящий
`pipeline run` — `ok=1`, на выходе то, что посчитал проект:

```json
{"sentence_count": 2, "sentences": ["Привет.", "Хочу обсудить сотрудничество."],
 "forbidden": [], "valid": true, "reason": ""}
```

## Дыра, которую вскрыл прогон

Импортированный плагин **не самодостаточен**: он работает с исходниками проекта-донора,
путь к которому передаётся переменной `WEDRA_DONOR_ROOT`. В манифесте такого
поля быть не может (`additionalProperties: false`), и зашивать абсолютный путь
чужой машины туда нельзя.

У WEDRA сейчас нет механизма объявить эту зависимость: ни в манифесте, ни в
реестре. Пока его нет, такой плагин нельзя поставить в общий реестр — он
работает только там, где донора положили рядом и задали переменную. Это долг,
а не особенность: до его закрытия «импорт проекта» даёт плагин для своей
машины, а не поставляемый артефакт.

## Проверка после импорта

- `wedra plugin validate <dir>` — манифест;
- `wedra plugin test <dir>` — тесты плагина;
- `registry validate` требует запись в `registry.yaml` с пином коммита,
  `plugin.test.yaml` минимум с тремя кейсами и совпадением `id` манифеста с
  именем записи. Без этого плагин не поставляется.
- После любой правки файлов доверие слетает: доверен **хэш содержимого**, а не
  имя. Новый хэш берётся из `GET /api/plugins/<id>/source` и вносится в
  `wedra-trust.yaml` — см. `SECURITY.md`.
