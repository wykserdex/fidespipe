# Версионирование Fidespipe

## Канонические оси

| Ось | Источник | Текущее значение | Правило |
|---|---|---|---|
| Product / application | `VERSION` | `0.34.0` | SemVer; тег `vX.Y.Z` совпадает с `VERSION` |
| Pipeline и plugin protocol | `protocol/VERSION` | `0.2` | меняется только при изменении контракта |
| Registry schema | `registry.yaml` | `0.1` | формат записи реестра |
| Plugin component | `plugin.yaml:version` | semver плагина | версия конкретного компонента |
| Plugin compatibility | `plugin.yaml:platform_api` | `^0.1` | совместимость с protocol API |
| MCP wire protocol | MCP server | `2025-06-18` (также `2024-11-05`) | внешний JSON-RPC контракт; ревизия выбирается при `initialize` |
| Registry source pin | `version` + `commit` | entry-specific | tag источника и immutable SHA |

`format_version` в pipeline — это версия protocol, а не версия Fidespipe.

## Product version

`VERSION` — единственный источник текущей версии приложения.

Схема нумерации: SemVer, тег `vX.Y.Z` совпадает с `VERSION`.

**Про смену схемы.** До 0.34.0 инкременты шли буквенными суффиксами
(`0.32a`, `0.32b`, `0.33c`), и это была осознанная ставка на частые точечные
релизы: шаг можно откатить, не трогая соседей. Ставка не окупилась, а цена
оказалась структурной: **Go принимает как версию модуля только SemVer**, и
тег вида `v0.33c` для него не существует. Из-за этого модуль нельзя было
поставить командой `go install github.com/wykserdex/fidespipe/cmd/fidespipe@latest` —
главным каналом распространения Go-CLI после готовых бинарников. Ломать
экосистему ради удобства внутреннего цикла — неправильный размен, поэтому:

- новые релизы нумеруются `X.Y.Z`, тег — `vX.Y.Z`;
- уже опубликованные буквенные теги (`v0.32c`, `v0.33c`, …) не переиспользуются
  и не переименовываются: они исторические записи, а не альтернативные версии;
- `VERSION` проверяется на соответствие SemVer шагом `versions` в
  `fidespipe check` и в релизном workflow, так что вернуться к буквам не получится
  случайно.

Отдельно про частоту: буквенный шаг позволял выпускать релиз на каждое
изменение, и за пять недель их набралось тридцать. Пинок к частым релизам —
не приглашение: релиз — это когда пользователю есть что получить, а не когда
очередь коммитов дошла до буквы. Порядок: тег на изменение, о котором можно
сказать одной строкой «что пользователь получит».

Правила:

- Номер не уменьшается и не переиспользуется. Следующий выбирается строго после
  последнего опубликованного тега.
- Версия плагина (`plugin.yaml:version`) — независимая ось, тоже SemVer.

Release workflow отклоняет tag, если он не совпадает с `VERSION`, и CI требует
заголовок `## <VERSION> ` в `CHANGELOG.md`. Перед релизом `VERSION` меняется с
рабочей версии на выбранную release-версию.

## Protocol version

`protocol/VERSION` и каталог `protocol/vX.Y/` описывают формат pipeline,
plugin manifest и ошибок. Product release может не менять protocol; изменение
protocol требует обновления protocol changelog, schema и conformance fixtures.

Поддерживаемые `format_version` перечисляются в коде и protocol documentation.
Неиспользуемые или экспериментальные номера не должны появляться в текущих
документах как active protocol.

## Registry pins

`registry.yaml` имеет собственную версию формата. Поле `version` в записи —
tag или branch источника, а `commit` — точный SHA для supply-chain pin. Они не
должны автоматически совпадать с product version: это разные системы
ссылок.

## Проверки

Механически проверяется (`.github/workflows/ci.yml`, шаг version invariants):

1. В `CHANGELOG.md` есть раздел `## <VERSION> ` — на любой строке, не обязательно
   вверху: верхним остаётся `## Unreleased`. Раньше здесь было написано «совпадает
   с верхним заголовком», и это не совпадало ни с файлом, ни с проверкой.
2. В `protocol/CHANGELOG.md` есть раздел `## v<protocol/VERSION> `.
3. `conformance/manifest.json` называет текущую protocol version.
4. Шаг `versions` в `fidespipe check` сверяет `VERSION` с README.md, README.en.md,
   docs/versioning.md и docs/architecture.md, а `verdoc` отвергает `VERSION` не по
   SemVer.

Правилом, а не проверкой, остаётся одно: release tag (в release.yml он
дополнительно сверяется с `VERSION` до публикации) не переиспользуется и не
перемещается — от перезаписи уже опубликованного тега workflow не защитит.

## Исторические обозначения

`v9`, `v10`, `v0.9` в старых сообщениях и исторические разборы, вынесенные из
публичного дерева, — исторические записи.
Они не являются альтернативными текущими версиями и не используются в новых
документах как источник version.
