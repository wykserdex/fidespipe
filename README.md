# Fidespipe

**Проверки, собранные из чужих инструментов: домен, почта, телефон, утечки
в коде, PE-файл — одной командой, с вердиктом на выходе.**

Инструменты здесь чужие: их пишут и правят люди, которые не знают друг друга.
Fidespipe сводит их к общему виду — JSON на входе, JSON на выходе, — ведёт
журнал каждого запуска и отдаёт спорные места человеку, а не решает за него.

**Кому это нужно.** Тем, кто разбирает чужое и опасается, что оно до него
дотянется: аналитику, открывшему письмо с вложением; инженеру, проверяющему
домен на утечки; пентестеру, гоняющему сканеры сотни раз в день. Инструменты
здесь чужие, и Fidespipe отвечает за то, чтобы они не трогали машину и не
оставались в ней.

```bash
fidespipe pipeline install email_check    # поставить проверку и её плагины
fidespipe pipeline run email_check.yaml   # прогнать; что на входе — в самом YAML
```

## Проверки, которые уже собраны

| проверка | что делает | что показывает |
|---|---|---|
| `email_check` | синтаксис, disposable-домен, MX-записи | MX-записи адреса и «одноразовый адрес» (да/нет) |
| `phones_audit` | батч телефонов в E.164 | сколько валидных, сколько нет, и список невалидных |
| `iban_check` | контрольная сумма IBAN | валиден ли счёт, форматированный номер, код банка |
| `secrets_scan` | секреты в коде | сколько находок, версия детектора, сами находки |
| `pe_triage` | PE-файл: архитектура, секции, импорты | разрядность, число секций, число импортируемых DLL |
| `near_dupe_check` | две строки на near-duplicate | расстояние, схожесть, «похожи ли» |
| `email_triage_chain` | почта → разбор → человек решает | риск и вердикт, которые правит человек |
| `csv_load` | CSV → разбор → гейт | число строк, заголовки, сами строки |

На выходе — поля и значения, а не готовый отчёт: решение «это нормально или
нет» принимает человек, и в `email_triage_chain` он правит вердикт руками.

Отдельно лежат примеры механики — `parallel_demo`, `foreach_step_demo`,
`when_demo`, `gate_demo`, `csv_foreach`, `csv_foreach_summary`,
`dir_snapshots`, `llm_text_chain`. Они показывают не задачу, а как устроены
ветки, циклы, условия и гейт; для работы они не нужны.

**Агент — не причина, а один из способов пользоваться.** Те же проверки и тот
же гейт доступны из терминала, из браузера и через MCP.

## Почему это работает

Договорённость между чужими инструментами — единственное, что нельзя
получить из коробки. Остальное — надстройки над ним:

| | что это даёт |
|---|---|
| **Контракт на границе** | входы и выходы плагина проверяются **до** запуска; битый YAML не падает в середине цепочки |
| **Журнал запуска** | каждый запуск остаётся на диске: события, контекст, артефакты; прогон можно продолжить с места обрыва |
| **Человек в петле** | `core/human_gate` ждёт **настоящего** решения, с потолком ожидания и одобрением по подписанной ссылке с любого устройства |
| **Доверие по хэшу** | «id@sha256:…»: правил файл — потерял доверие; имя плагина доверия не даёт |
| **Изоляция** | недоверенный код уходит в песочницу: bubblewrap на Linux, AppContainer на Windows (каталог плагина только на чтение, сеть запрещена) |
| **Каталог с донорами** | 100 плагинов, магазин с установкой, типизированные рецепты для Go-программ, бинарников и скриптов с проверкой sha256 |
| **Пишущий инструмент** | редактор плагинов в браузере и `fidespipe plugin import` — разбор чужого Python-проекта в готовый плагин |
| **Планировщик** | локальный демон с **долговечной очередью**: слот, однажды отработавший, не запустится дважды; прерванная работа не перезапускается молча |
| **Развёртывание** | Docker и systemd — для сервера, где проверки идут по расписанию |

```text
плагин A → плагин B → [человек решает] → плагин C → результат
```

Точки, через которые Fidespipe расширяется:

| Поверхность | Инструменты |
|---|---|
| Агенты (MCP) | 8 инструментов: `list_plugins`, `describe_plugin`, `validate_pipeline`, `plan_pipeline`, `run_pipeline`, `get_run`, `cancel_run`, `exec_plugin` (выключен по умолчанию) |
| Плагины | свой процесс с JSON на входе и выходе; контракт — в [PROTOCOL.md](protocol/v0.2/PROTOCOL.md), версия — в [protocol/VERSION](protocol/VERSION) |
| Реестр | запись плагина проходит гейт конформности и попадает в `registry.yaml`; проверяет шаг `registry` в CI |
| Импорт | чужой Python-проект становится плагином через `fidespipe plugin import` |


Консоль запускается командой `fidespipe gui`: раны с таймлайном, пайплайны с DAG,
каталог плагинов, редактор и магазин.

![Сборка цепочки и запуск: главная, редактор со связанными шагами, свойства шага, YAML цепочки и ран](demo.gif)

Полный обзор консоли — длинное демо в [`docs/demo.gif`](docs/demo.gif).

Проект жив. Сейчас в работе 0.35.0: одобрение гейта по подписанной ссылке,
долговечная очередь слотов, типизированные рецепты доноров, ретенция прогонов,
алерты расписания с настоящей доставкой, потолок ожидания на гейте, Docker и
systemd. Состав изменений — в [CHANGELOG](CHANGELOG.md).

## Попробовать

Собери бинарник из исходников (нужен Go 1.26+). Из корня репозитория:

```bash
go build -o fidespipe ./cmd/fidespipe
./fidespipe demo
```

Готовые сборки есть на странице [Releases](https://github.com/wykserdex/fidespipe/releases), но только для опубликованных версий (см. раздел «Релизы» ниже).

Демо работает без Git, Python и сети и проверяет, что Fidespipe запускается. Оно использует встроенные модули, а не стороннюю цепочку плагинов. На Windows бинарник называется `fidespipe.exe` — команды ниже те же, `./` не нужен.

## Все команды

Справочник. Начать проще с `fidespipe demo` — он работает без Git, Python и
сети.

```bash
fidespipe demo                                  # автономная цепочка: ноль git, ноль Python, ноль сети
fidespipe doctor                                # что сломано в окружении и что доустановить
fidespipe plugin list                           # 100 плагинов
fidespipe plugin search ssl                     # поиск по названию и описанию
fidespipe plugin install sherlock               # поставить из реестра, вместе с донором
fidespipe plugin create my_plugin               # создать плагин из шаблона
fidespipe plugin import ./чужой-проект           # разобрать чужой проект в плагин
fidespipe plugin validate my_plugin             # проверить манифест
fidespipe plugin test my_plugin                 # прогнать его тесты
fidespipe pipeline validate pipeline.yaml       # проверить пайплайн ДО запуска
fidespipe pipeline run pipeline.yaml            # выполнить
fidespipe runs list                             # журнал запусков
fidespipe runs show <run_id>                    # события, контекст, артефакты
fidespipe runs resume <run_id> pipeline.yaml     # продолжить с места обрыва
fidespipe schedule                              # расписание цепочек
fidespipe daemon                                # демон: тикает и запускает подошедшее
fidespipe gui                                   # консоль в браузере
fidespipe mcp                                   # сервер MCP для агентов
fidespipe approve <run_id> <step_id> --link     # подписанная ссылка одобрения
fidespipe check                                 # единая проверка проекта (15 гейтов)
```

## Найти и поставить плагин

В репозитории и в реестре — **100 плагинов**: 5 official и 95 community. Из них
**65** работают на голом Python 3 и не требуют ничего; ещё 35 объявляют донора
через `runtime.requires`, и `install` ставит его сам — ровно
`pip install пакет==версия`.

У пяти плагинов донора нет на PyPI, и он ставится **типизированным рецептом** в
манифесте:

```yaml
runtime:
  donor:
    kind: go        # go | binary | script
    name: gospider
    version: v1.1.6
    module: github.com/jaeles-project/gospider
    bin_env: GOSPIDER_BIN
```

Три вида: `go` (`go install module@version`, контрольные суммы проверяет прокси
Go), `binary` (готовый файл: `url` + `sha256`), `script` (`url` + `sha256` +
интерпретатор). **sha256 обязателен** для `binary` и `script`, и сверяется до
распаковки: качать исполняемый код из сети, не сверив хеш, — это не
установка, а закладка. Адрес — только `https`.

Донор ставится **вне каталога плагина** — в `<plugins>/.donors/<id>/`. Это не
выбор вкуса: доверие выдаётся по хэшу содержимого каталога, и установка донора
внутрь изменила бы хэш, то есть плагин перестал бы быть доверенным ровно в
момент установки.

**Числа выше — свойство каталога; состояние конкретной машины меряется, а не
объявляется.** `fidespipe doctor` пересчитывает каждый плагин тем же Python,
которым запускается сама Fidespipe, и печатает, сколько готовы и что доустановить.
Она ничего не ставит и ничего не запускает.

**Про слово «community».** Сейчас все 100 плагинов написаны владельцем
репозитория и лежат в нём же: у всех 100 записей реестра `source` — один и тот
же `https://github.com/wykserdex/fidespipe`. Посторонних авторов и внешних
источников нет ни одного. «Community» означает поставку вне ядра — это всё,
что не входит в поддерживаемый набор `plugins/official/`, — а не «написано
сторонним автором». Поле `author` в манифестах сейчас плейсхолдер, а не имена
людей; у official-манифестов его нет вовсе.

**Важно:** плагин — это скрипт на Python, который либо делает дело сам, либо
является обёрткой над внешним инструментом. Пока инструмент не установлен,
плагин честно отдаёт доменную ошибку `<имя>_not_installed` с командой
установки, а не падает. Требования каждого плагина перечислены в его
`README.md`.

## Границы

Честные пределы, чтобы не приходилось угадывать.

- **Всё происходит на одной машине.** Оркестрация — это DAG внутри одного
  процесса: шаги, `when`, `foreach`, `parallel_group` с барьером. Распределённого
  планировщика, очередей между машинами и сервис-дискавери нет.
- **Планировщик локальный.** `fidespipe daemon` тикает раз в минуту и запускает
  то, что подошло по cron, из долговечной очереди: слот занимается до запуска,
  поэтому перезапуск демона не приводит к повторному выполнению, а работа,
  застигнутая при смерти демона, помечается прерванной. Входящих триггеров нет:
  расписание только по времени.
- **Это бинарник, а не облако.** Аккаунтов, телеметрии и сервера, который
  хранит твои данные за тебя, нет: каталог `plugins/` и журналы в `var/runs/`.
  Консоль по умолчанию слушает `127.0.0.1`; вынос наружу — осознанный флаг
  оператора (`--listen`, `--allow-remote`). Внешние сервисы подключаются не как
  «интеграции Fidespipe», а как обычные плагины с твоим ключом из переменной
  окружения.
- **Плагин попадает в реестр не потому, что написан, а потому, что проходит
  гейт конформности** и честно объявляет `permissions`. 100 плагинов — не
  витрина: 65 работают на голом Python 3, 35 объявляют донора, и донора ставит
  сам `install`.

## Стабильность формата пайплайна

**Что означает версия формата.** `format_version` в YAML — это версия
*протокола формата*, а не версия приложения. Оси независимы: версия Fidespipe живёт
в файле `VERSION` и меняется чаще, протокол формата — в `protocol/VERSION` и
меняется редко. Проверяемо: `fidespipe pipeline validate` на файле с незнакомым
`format_version` даёт **ошибку** `E_FORMAT_VERSION`, а не warning; пустое поле —
warning `W_FORMAT_VERSION_MISSING`. Поддерживаемые значения перечислены в коде
и не расширяются молча: сегодня это ровно `"0.1"` и `"0.2"`.

**Что обещается.** Формат не заморожен, но обязательство конкретное:

> Пока значение `format_version` в твоём файле не менялось, пайплайн, который
> валидировался, валидируется и запускается.

Обещание держится на вещах, которые можно проверить, а не поверить:

- **Два значения — два живых формата.** `"0.1"` не объявлен устаревшим: он
  принимается наравне с `"0.2"`, пайплайны с ним лежат в `examples/`, и их
  прогоняет шаг `pipelines` (`validate` + `lint` + `plan`) полного `fidespipe check` —
  тот же прогон, что идёт в CI.
- **Ломающая правка формата не может быть молчаливой.** По
  [GOVERNANCE.md](GOVERNANCE.md) изменение протокола требует публичного
  предложения с указанием влияния на совместимость, шагов миграции, тестов и той
  оси версий, которую оно меняет; [CONTRIBUTING.md](CONTRIBUTING.md) требует
  миграционной записки и тестов совместимости. Результат обязан появиться в
  `protocol/CHANGELOG.md` вместе с новым значением в `protocol/VERSION` и
  каталогом `protocol/vX.Y/`.
- **Контракт проверяется механически.** Гейт `errcodes` сверяет коды ошибок в Go
  с `protocol/v0.2/ERRORS.md`; гейт `versions` сверяет версии в README и docs с
  репозиторием; гейт `schemas` сверяет `schemas/` с примерами и манифестами.

**Что всё равно может измениться** — честный список, без которого обещание выше
было бы пустым:

- **Формат расширяется.** Могут появиться новые необязательные поля и новые коды
  ошибок — такое уже было (`snapshot_lost`, `E_AGENT_EXEC_AUDIT`). Старый YAML от
  этого не ломается.
- **Обратной совместимости наоборот нет.** Разбор пайплайна строгий
  (`KnownFields(true)` в `internal/pipeline/parser.go`): бинарник Fidespipe старше
  твоего файла откажется его открывать, а не промолчит. Старый бинарник читает
  старые файлы, а не новые.
- **Коды ошибок и имена MCP-инструментов — не замороженный API.** Гейты следят,
  чтобы код в Go совпадал с контрактом, а README — с реально принимаемыми
  инструментами, но это проверка согласованности, а не запрет добавить новое или
  переименовать старое.
- **Прогон зависит от плагинов.** Если плагин удалён из реестра или его донор не
  установлен, цепочка не запустится. Это не про формат.
- **Обещание не про CLI и не про интерфейс.** Флаги команд, набор MCP-инструментов
  и поведение консоли живут на оси приложения и меняются вместе с релизом.
- **Формат не заморожен навечно.** Проект в ветке 0.x, и
  [SECURITY.md](SECURITY.md) прямо говорит, что фиксы получает только текущая
  линия. Новая версия протокола допустима — обязана только быть объявлена так,
  как описано выше.

Разбор с привязкой к коду — в [docs/format-compatibility.md](docs/format-compatibility.md).

## Пример пайплайна

```yaml
format_version: "0.2"
pipeline:
  name: example
  input:
    text: "hello world hello"
  steps:
    - id: stats
      plugin: plugins/community/text_analyzer
    - id: review
      plugin: core/human_gate
      form:
        - { field: steps.stats.words, editable: false }
      actions: [accept, reject]
```

Проверь описание до запуска, затем выполни пайплайн:

```bash
./fidespipe pipeline validate pipeline.yaml
./fidespipe pipeline run pipeline.yaml
```

Шаг `review` ждёт твоего решения — напечатай `a`, чтобы принять, или `r`, чтобы отклонить. В пайплайне или CI, где ввода нет, добавь `--yes`, чтобы принять всё автоматически. `--no-auto-approve` — обратное: гейт будет ждать человека, и без ввода ран на нём остановится.

**Без терминала.** На сервере, где терминала нет, решение принимают по
**подписанной ссылке**: демон печатает её, человек открывает с телефона и
решает. Ссылка подписана ключом, живёт час и работает один раз. Подробности —
в [docs/deployment.md](docs/deployment.md).

Полный формат пайплайна и готовые примеры — в [быстром старте](docs/quickstart.md) и в [`examples/`](examples/).

## Релизы

Стабильные сборки — в [GitHub Releases](https://github.com/wykserdex/fidespipe/releases):
`fidespipe-{linux,darwin,windows}-{amd64,arm64}`, legacy `tool-*`, `fidespipegui-windows-*.exe`,
conformance-пакет, `SHA256SUMS`, SBOM (`sbom.spdx.json`) и build provenance.
Релизный воркфлоу подписывает `SHA256SUMS` и SBOM ключом без секретов
(Sigstore keyless: Fulcio + Rekor, токен раннера, никаких секретов в
репозитории) и проверяет подпись до публикации. Первый прогон этой схемы
ещё не состоялся — что уже проверено и что ждёт CI, написано честно в
[цепочке поставки](docs/supply-chain.md).
Тег релиза (`vX.Y.Z`) совпадает с [`VERSION`](VERSION) — сейчас `0.35.0`;
protocol version — [`protocol/VERSION`](protocol/VERSION) (`0.2`), версии независимы.
Текущий релиз — `0.35.0`; бинарники для своей системы лежат на странице [Releases](https://github.com/wykserdex/fidespipe/releases). Состав изменений — в [CHANGELOG](CHANGELOG.md).

## Безопасность и статус

Плагины — исполняемый код: локальный запуск сам по себе не делает их безопасными. Проверяй источник плагина и ограничения запуска; подробности — в [модели безопасности](SECURITY.md).

Объявленная сеть плагина — это либо весь интернет (`any_host: true`), либо отсутствие сети. Фильтра по конкретным хостам нет ни на одной платформе (см. [SECURITY.md](SECURITY.md#egress-filtering-proxy-built-kernel-enforcement-still-missing)). Изоляция внешнего кода (`sandbox: untrusted`) работает на Linux (bubblewrap) и
на Windows (AppContainer) — обе измерены враждебными тестами: каталог плагина
только на чтение, каталог без выдачи недостижим, сеть запрещена. На macOS
внешний код не запускается. Сеть внутри контейнера на Windows выдаётся через
capability `internetClient` и только если она реально действует на хосте — иначе
плагин с заявленной сетью не запускается вовсе, с объяснением (см.
[docs/windows-network-capability.md](docs/windows-network-capability.md)).

Fidespipe находится в активной разработке версии 0.x, поэтому интерфейс и формат могут меняться. Про формат сказано точнее в разделе «Стабильность формата пайплайна»: версия формата меняется по правилам протокола, а молчаливых ломающих правок быть не может — но и новые поля, и новые коды ошибок появляются.
