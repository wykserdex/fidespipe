# WEDRA

**Локальная платформа для запуска чужих инструментов: контракт, доверие,
журнал запуска и человек в петле.**

Платформа — потому что платформа это не «ещё один оркестратор». Оркестратор
выполняет цепочки; **платформа задаёт контракт, поверх которого цепочки
выполнять можно по-разному**. У WEDRA контракт один: плагин — отдельный
процесс, на входе JSON, на выходе JSON, версия протокола объявлена и
версионируется отдельно от приложения. Всё остальное — надстройки над ним, и
писать их может кто угодно:

- **раннер цепочек** — DAG из шагов, ветки `parallel_group` с барьером, `when`,
  `foreach`;
- **планировщик** — локальный демон с долговечной очередью слотов;
- **магазин и редактор** — каталог плагинов с установкой доноров и браузерный
  редактор;
- **MCP** — агенты получают те же инструменты, что и человек;
- **импорт** — чужой Python-проект превращается в плагин;
- **реестр и протокол** — версия формата, правило совместимости, гейт
  конформности в CI.

Запуск нескольких CLI подряд и склейка вывода руками — это то, что платформа
делает *внутри*, и меньшая часть того, что она даёт. Вот что даёт:

| | что даёт WEDRA |
|---|---|
| **Контракт на границе** | входы и выходы плагина проверяются **до** запуска; битый YAML не падает в середине цепочки |
| **Журнал запуска** | каждый запуск остаётся на диске: события, контекст, артефакты; прогон можно продолжить с места обрыва |
| **Человек в петле** | `core/human_gate` ждёт **настоящего** решения, с потолком ожидания и одобрением по подписанной ссылке с любого устройства |
| **Изоляция** | недоверенный код уходит в песочницу (bubblewrap на Linux); AppContainer на Windows измерен, но не включён |
| **Доверие по хэшу** | «id@sha256:…»: правил файл — потерял доверие; имя плагина доверия не даёт |
| **Планировщик** | локальный демон с **долговечной очередью**: слот, однажды отработавший, не запустится дважды; прерванная работа не перезапускается молча |
| **Каталог с донорами** | 100 плагинов, магазин с установкой, типизированные рецепты для Go-программ, бинарников и скриптов с проверкой sha256 |
| **Пишущий инструмент** | редактор плагинов в браузере и `wedra plugin import` — разбор чужого Python-проекта в готовый плагин |
| **Агенты** | MCP: агент может предложить план и запустить цепочку, а решение остаётся за человеком |
| **Развёртывание** | Docker и systemd — для сервера, где цепочки идут по расписанию |

```text
плагин A → плагин B → [человек решает] → плагин C → результат
```

Консоль запускается командой `wedra gui`: раны с таймлайном, пайплайны с DAG,
каталог плагинов, редактор и магазин.

![Сборка цепочки и запуск: главная, редактор со связанными шагами, свойства шага, YAML цепочки и ран](demo.gif)

Полный обзор консоли — длинное демо в [`docs/demo.gif`](docs/demo.gif).

Проект жив. Сейчас в работе 0.35.0: одобрение гейта по подписанной ссылке,
долговечная очередь слотов, типизированные рецепты доноров, ретенция прогонов,
алерты расписания с настоящей доставкой, потолок ожидания на гейте, Docker и
systemd. Состав изменений — в [CHANGELOG](CHANGELOG.md).

## Попробовать

Собери бинарник из исходников (нужен Go 1.26+). Из корня репозитория:

```bash
go build -o wedra ./cmd/wedra
./wedra demo
```

Готовые сборки есть на странице [Releases](https://github.com/wykserdex/wedra/releases), но только для опубликованных версий (см. раздел «Релизы» ниже).

Демо работает без Git, Python и сети и проверяет, что WEDRA запускается. Оно использует встроенные модули, а не стороннюю цепочку плагинов. На Windows бинарник называется `wedra.exe` — команды ниже те же, `./` не нужен.

## Что можно сделать

```bash
wedra demo                                  # автономная цепочка: ноль git, ноль Python, ноль сети
wedra doctor                                # что сломано в окружении и что доустановить
wedra plugin list                           # 100 плагинов
wedra plugin search ssl                     # поиск по названию и описанию
wedra plugin install sherlock               # поставить из реестра, вместе с донором
wedra plugin create my_plugin               # создать плагин из шаблона
wedra plugin import ./чужой-проект           # разобрать чужой проект в плагин
wedra plugin validate my_plugin             # проверить манифест
wedra plugin test my_plugin                 # прогнать его тесты
wedra pipeline validate pipeline.yaml       # проверить пайплайн ДО запуска
wedra pipeline run pipeline.yaml            # выполнить
wedra runs list                             # журнал запусков
wedra runs show <run_id>                    # события, контекст, артефакты
wedra runs resume <run_id> pipeline.yaml     # продолжить с места обрыва
wedra schedule                              # расписание цепочек
wedra daemon                                # демон: тикает и запускает подошедшее
wedra gui                                   # консоль в браузере
wedra mcp                                   # сервер MCP для агентов
wedra approve <run_id> <step_id> --link     # подписанная ссылка одобрения
wedra check                                 # единая проверка проекта (15 гейтов)
```

## Найти и поставить плагин

В репозитории и в реестре — **100 плагинов**: 5 official и 95 community. Из них
**65** работают на голом Python 3 и не требуют ничего; ещё 35 объявляют донора
через `runtime.requires`, и `install` ставит его сам — ровно
`pip install пакет==версия`.

У пяти плагинов донора нет на PyPI, и он ставится **типизированным рецептом** в
манифесте:

```yaml
runtime:
  donor:
    kind: go        # go | binary | script
    name: gospider
    version: v1.1.6
    module: github.com/jaeles-project/gospider
    bin_env: GOSPIDER_BIN
```

Три вида: `go` (`go install module@version`, контрольные суммы проверяет прокси
Go), `binary` (готовый файл: `url` + `sha256`), `script` (`url` + `sha256` +
интерпретатор). **sha256 обязателен** для `binary` и `script`, и сверяется до
распаковки: качать исполняемый код из сети, не сверив хеш, — это не
установка, а закладка. Адрес — только `https`.

Донор ставится **вне каталога плагина** — в `<plugins>/.donors/<id>/`. Это не
выбор вкуса: доверие выдаётся по хэшу содержимого каталога, и установка донора
внутрь изменила бы хэш, то есть плагин перестал бы быть доверенным ровно в
момент установки.

**Числа выше — свойство каталога; состояние конкретной машины меряется, а не
объявляется.** `wedra doctor` пересчитывает каждый плагин тем же Python,
которым запускается сама WEDRA, и печатает, сколько готовы и что доустановить.
Она ничего не ставит и ничего не запускает.

**Про слово «community».** Сейчас все 100 плагинов написаны владельцем
репозитория и лежат в нём же: у всех 100 записей реестра `source` — один и тот
же `https://github.com/wykserdex/wedra`. Посторонних авторов и внешних
источников нет ни одного. «Community» означает поставку вне ядра — это всё,
что не входит в поддерживаемый набор `plugins/official/`, — а не «написано
сторонним автором». Поле `author` в манифестах сейчас плейсхолдер, а не имена
людей; у official-манифестов его нет вовсе.

**Важно:** плагин — это скрипт на Python, который либо делает дело сам, либо
является обёрткой над внешним инструментом. Пока инструмент не установлен,
плагин честно отдаёт доменную ошибку `<имя>_not_installed` с командой
установки, а не падает. Требования каждого плагина перечислены в его
`README.md`.

## Что даёт WEDRA

- **Один повторяемый запуск.** Порядок шагов и связи между ними описаны в YAML.
- **Контракт на границе плагина.** Плагины запускаются отдельными процессами; их входы и выходы проверяются.
- **Выбор способа получить итог.** Смотри вывод шагов или добавь явный плагин-форматтер.
- **Контроль человека — по необходимости.** Добавь `core/human_gate`, если перед продолжением нужен просмотр и решение.
- **MCP — дополнительно.** Агент может вызывать инструменты WEDRA через MCP; для обычного локального запуска MCP не нужен. Подробности — в [документации MCP](docs/mcp.md).

Точки, через которые платформа расширяется:

| Поверхность | Инструменты |
|---|---|
| Агенты (MCP) | 8 инструментов: `list_plugins`, `describe_plugin`, `validate_pipeline`, `plan_pipeline`, `run_pipeline`, `get_run`, `cancel_run`, `exec_plugin` (выключен по умолчанию) |
| Плагины | свой процесс с JSON на входе и выходе; контракт — в [PROTOCOL.md](protocol/v0.2/PROTOCOL.md), версия — в [protocol/VERSION](protocol/VERSION) |
| Реестр | запись плагина проходит гейт конформности и попадает в `registry.yaml`; проверяет шаг `registry` в CI |
| Импорт | чужой Python-проект становится плагином через `wedra plugin import` |

## Чего WEDRA не делает

Позиционирование написано прямо, потому что чаще всего WEDRA разочаровывает
именно этим списком, а не составом функций.

- **Планировщик локальный, а не облачный.** `wedra daemon` тикает раз в минуту
  и запускает то, что подошло по cron, из **долговечной очереди**: слот
  занимается до запуска, поэтому перезапуск демона не приводит к повторному
  выполнению, а работа, застигнутая при смерти демона, помечается прерванной и
  по ней уходит оповещение. Демон живёт на вашей машине, запускается явно и
  держит блокировку, чтобы второй не стартовал; решение о запуске всё равно
  принимает человек. Входящих триггеров по-прежнему нет: расписание только по
  времени.
- **Не станет облаком и не будет продаваться как SaaS-интеграция.** Аккаунтов,
  телеметрии и сервера, который хранит твои данные за тебя, нет и не будет: это
  бинарник, каталог `plugins/` и журналы в `var/runs/`. Консоль по умолчанию
  слушает `127.0.0.1`; вынос её наружу — осознанный флаг оператора (`--listen`,
  `--allow-remote`), а не режим работы. Внешние сервисы подключаются не как
  «интеграции WEDRA», а как обычные плагины с твоим ключом из переменной
  окружения.
- **Не гонится за числом плагинов.** 100 плагинов в реестре — не витрина: 65
  работают на голом Python 3, 35 объявляют донора, и донора ставит уже сам
  `install` (числа и как их перепроверить — в разделе «Найти и поставить
  плагин»). Плагин попадает в реестр не потому, что написан, а потому, что
  проходит гейт конформности и честно объявляет `permissions`; это проверяет
  шаг `registry` в CI.
- **Не строит облачную оркестрацию ради облачной оркестрации.** Оркестрация
  здесь — это DAG внутри одного процесса: шаги, `when`, `foreach`,
  `parallel_group` с барьером. Ни распределённого планировщика, ни очередей между
  машинами, ни сервис-дискавери: всё, что делает WEDRA, происходит на одной
  машине, в одном ране.

**Что WEDRA делает:** детерминированный прогон цепочки, описанной в YAML, где
решение о продолжении остаётся за человеком. Шаги и связи проверяются до
запуска, человек стоит в петле на `core/human_gate`, а не наблюдает постфактум.

## Стабильность формата пайплайна

**Что означает версия формата.** `format_version` в YAML — это версия
*протокола формата*, а не версия приложения. Оси независимы: версия WEDRA живёт
в файле `VERSION` и меняется чаще, протокол формата — в `protocol/VERSION` и
меняется редко. Проверяемо: `wedra pipeline validate` на файле с незнакомым
`format_version` даёт **ошибку** `E_FORMAT_VERSION`, а не warning; пустое поле —
warning `W_FORMAT_VERSION_MISSING`. Поддерживаемые значения перечислены в коде
и не расширяются молча: сегодня это ровно `"0.1"` и `"0.2"`.

**Что обещается.** Формат не заморожен, но обязательство конкретное:

> Пока значение `format_version` в твоём файле не менялось, пайплайн, который
> валидировался, валидируется и запускается.

Обещание держится на вещах, которые можно проверить, а не поверить:

- **Два значения — два живых формата.** `"0.1"` не объявлен устаревшим: он
  принимается наравне с `"0.2"`, пайплайны с ним лежат в `examples/`, и их
  прогоняет шаг `pipelines` (`validate` + `lint` + `plan`) полного `wedra check` —
  тот же прогон, что идёт в CI.
- **Ломающая правка формата не может быть молчаливой.** По
  [GOVERNANCE.md](GOVERNANCE.md) изменение протокола требует публичного
  предложения с указанием влияния на совместимость, шагов миграции, тестов и той
  оси версий, которую оно меняет; [CONTRIBUTING.md](CONTRIBUTING.md) требует
  миграционной записки и тестов совместимости. Результат обязан появиться в
  `protocol/CHANGELOG.md` вместе с новым значением в `protocol/VERSION` и
  каталогом `protocol/vX.Y/`.
- **Контракт проверяется механически.** Гейт `errcodes` сверяет коды ошибок в Go
  с `protocol/v0.2/ERRORS.md`; гейт `versions` сверяет версии в README и docs с
  репозиторием; гейт `schemas` сверяет `schemas/` с примерами и манифестами.

**Что всё равно может измениться** — честный список, без которого обещание выше
было бы пустым:

- **Формат расширяется.** Могут появиться новые необязательные поля и новые коды
  ошибок — такое уже было (`snapshot_lost`, `E_AGENT_EXEC_AUDIT`). Старый YAML от
  этого не ломается.
- **Обратной совместимости наоборот нет.** Разбор пайплайна строгий
  (`KnownFields(true)` в `internal/pipeline/parser.go`): бинарник WEDRA старше
  твоего файла откажется его открывать, а не промолчит. Старый бинарник читает
  старые файлы, а не новые.
- **Коды ошибок и имена MCP-инструментов — не замороженный API.** Гейты следят,
  чтобы код в Go совпадал с контрактом, а README — с реально принимаемыми
  инструментами, но это проверка согласованности, а не запрет добавить новое или
  переименовать старое.
- **Прогон зависит от плагинов.** Если плагин удалён из реестра или его донор не
  установлен, цепочка не запустится. Это не про формат.
- **Обещание не про CLI и не про интерфейс.** Флаги команд, набор MCP-инструментов
  и поведение консоли живут на оси приложения и меняются вместе с релизом.
- **Формат не заморожен навечно.** Проект в ветке 0.x, и
  [SECURITY.md](SECURITY.md) прямо говорит, что фиксы получает только текущая
  линия. Новая версия протокола допустима — обязана только быть объявлена так,
  как описано выше.

Разбор с привязкой к коду — в [docs/format-compatibility.md](docs/format-compatibility.md).

## Пример пайплайна

```yaml
format_version: "0.2"
pipeline:
  name: example
  input:
    text: "hello world hello"
  steps:
    - id: stats
      plugin: plugins/community/text_analyzer
    - id: review
      plugin: core/human_gate
      form:
        - { field: steps.stats.words, editable: false }
      actions: [accept, reject]
```

Проверь описание до запуска, затем выполни пайплайн:

```bash
./wedra pipeline validate pipeline.yaml
./wedra pipeline run pipeline.yaml
```

Шаг `review` ждёт твоего решения — напечатай `a`, чтобы принять, или `r`, чтобы отклонить. В пайплайне или CI, где ввода нет, добавь `--yes`, чтобы принять всё автоматически. `--no-auto-approve` — обратное: гейт будет ждать человека, и без ввода ран на нём остановится.

**Без терминала.** На сервере, где терминала нет, решение принимают по
**подписанной ссылке**: демон печатает её, человек открывает с телефона и
решает. Ссылка подписана ключом, живёт час и работает один раз. Подробности —
в [docs/deployment.md](docs/deployment.md).

Полный формат пайплайна и готовые примеры — в [быстром старте](docs/quickstart.md) и в [`examples/`](examples/).

## Релизы

Стабильные сборки — в [GitHub Releases](https://github.com/wykserdex/wedra/releases):
`wedra-{linux,darwin,windows}-{amd64,arm64}`, legacy `tool-*`, `wedragui-windows-*.exe`,
conformance-пакет, `SHA256SUMS`, SBOM (`sbom.spdx.json`) и build provenance.
Релизный воркфлоу подписывает `SHA256SUMS` и SBOM ключом без секретов
(Sigstore keyless: Fulcio + Rekor, токен раннера, никаких секретов в
репозитории) и проверяет подпись до публикации. Первый прогон этой схемы
ещё не состоялся — что уже проверено и что ждёт CI, написано честно в
[цепочке поставки](docs/supply-chain.md).
Тег релиза (`vX.Y.Z`) совпадает с [`VERSION`](VERSION) — сейчас `0.34.0`;
protocol version — [`protocol/VERSION`](protocol/VERSION) (`0.2`), версии независимы.
Текущий релиз — `0.34.0`; бинарники для своей системы лежат на странице [Releases](https://github.com/wykserdex/wedra/releases). Состав изменений — в [CHANGELOG](CHANGELOG.md).

## Безопасность и статус

Плагины — исполняемый код: локальный запуск сам по себе не делает их безопасными. Проверяй источник плагина и ограничения запуска; подробности — в [модели безопасности](SECURITY.md).

Объявленная сеть плагина — это либо весь интернет (`any_host: true`), либо отсутствие сети. Фильтра по конкретным хостам нет ни на одной платформе (см. [SECURITY.md](SECURITY.md#egress-filtering-proxy-built-kernel-enforcement-still-missing)). Изоляция внешнего кода (`sandbox: untrusted`) работает на Linux (bubblewrap); на Windows AppContainer измерен и доказан, но **не включён** — до включения смена границы безопасности требует отдельных враждебных тестов, а не «изоляция работает по замеру». На macOS внешний код не запускается.

WEDRA находится в активной разработке версии 0.x, поэтому интерфейс и формат могут меняться. Про формат сказано точнее в разделе «Стабильность формата пайплайна»: версия формата меняется по правилам протокола, а молчаливых ломающих правок быть не может — но и новые поля, и новые коды ошибок появляются.
